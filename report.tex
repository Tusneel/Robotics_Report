\section{Introduction}

For this project our group has created a robot
in Gazebo Harmonic that can traverse from the
start of the Meston building to the end goal
whilst avoiding fire. To help it on its journey
it has various sensors such as a camera, a thermometer,
and a fire extinguisher. The robot builds a path using an A* 
search algorithm, if it runs into an obstacle it 
will use the same algorithm to reroute until it 
reaches the goal or determines there is no valid path 
to the goal.

\section{Robot}

THe robot we have chosen was obtained by us on GitHub \cite{robot} 
After carefully going through multiple candidates we eventually 
found one to satisfy our needs. Initially we even planned on 
building our own due to how much we were struggling to 
find a suitable option, but we were advised against it. 
Our main motivation was finding a robot that has the sensors 
we needed though we soon realised it was easier to add them 
ourselves, which led to us taking the new approach that we did.

\section{Task}

The main objective of this was initially to compare two 
different search algorithms, BFS and DFS, to see which 
one would make it to the end quicker but found the search 
algorithms to be to simple and inefficient for the task. 
As such, we made the cruicial decision to swap to A* search 
instead, a more efficient search algorithm and far more 
fitting for the environment. Quite frankly it didn't make sense 
to use two slow search algorithms in a burning building. Since this 
is now just one search algorithm the task for our project has changed. 
The new task has less emphasis on the search algorithms and more 
on the robot navigating obstacles. The task is for the robot to make 
it from start to finish navigating the fire using its sensors. 
If it finds there is a path blocked it will use its fire extinguisher. 
If both paths are blocked it will instead navigate back to the start. 
Finally, if there is a path unblocked, it will make its way through 
to reach the goal.

\section{Simulation Environment}

For the environment, we used the fire escape map of Meston and brought 
it into Gazebo. We specifically chose the ground floor for the sake of 
having a flat surface so we wouldn't have to worry about elevation. 
Another change we made was to make the fire static. We attempted to use 
Conway's game of life to determine the robots movement but decided it 
wasn't the best use for it. It didn't make the fire dynamic in any way 
that was meaningful. As such we had settled on static fire on the ground 
floor of the Meston building.

\section{Libraries and Tools}
Our project used ROS2-jazzy \cite{ros2} with the Gazebo simulation enviroment 
\cite{gazebodocs}. In order to develop with ROS we used the rclpy python API 
provided with ROS*. Gazebo provided an easy framework for modifying the robot 
we found, with the robot and world being written using custom XML files, and 
provided a set of useful custom sensors of which we used RGBD Sensor and Odometry. 
In addition to these we also used RVIZ to visualise our ROS topics which helped 
with debugging.

\section{Discussion}

\subsection{Strengths}
The most major strength of our robot design is its resilience and ability 

to re-evaluate its approach when something goes wrong. For example, when 

our robot's plan puts it in harms way, it is able to acknowledge this, 
reverse 
out of danger and then, when safe, create a new plan taking into 
account its new 
found knowledge of the environment. 

\subsection{Limitations}
The major limitations of our robot consist of; the design, currently our model is 
extremely ditsy and clumsy due to it only having two wheels. Ideally we would like 
to add a third or even forth wheel, tho this is discussed further in the next section. 
Additionally, it is slightly tailored to our Meston domain as it was unfeasible for us 
to model the intricacies of a real burning building thus it may fail in other more expanded 
enviornments. 


\subsection{Future Work}
If given more time to work on this project, there are many areas we would like to expand upon. 
However, if we had to pick three they would be:
- Exploring more uninformed algorithms such as decision trees. 
Alternatively, seeing the 
effect on efficiency of different heuristics 
when used in our A* search. 
- Testing other sensors and robot designs and how different robot 
designs allow us to navigate 
our environment differently.
- Testing how our developed software functions when applied to a physical 
robot and world. 
Additionally, seeing how we would have to adapt our code 
to the inconsistencies of a non-simulated environment.

\section{Conclusion}
In conclusion, our robot can successfully navigate the partially observable environment we provide it with. 
We achieved this using ros2 and modelling the problem in gazebo. 
Finally, we have many aspects of this project we would love to expand upon given additional time and resources.
